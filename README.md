# kill-or-ship

> 1등을 뽑지 말고, 버릴 것부터 골라라.

PMF 검증, 마케팅 전략, 사이드 프로젝트에 대한 구조적 피드백을 주는 자기 진화형 Claude 스킬입니다.

표면 질문에 즉답하지 않습니다. 되물어서 본인이 진짜 질문에 도달하게 하고, 본질을 짚고, 버릴 것부터 고릅니다. 세션마다 자기 비판을 저널에 남기고, 같은 약점이 누적되면 스킬이 자기 자신을 수정합니다.

---

## 언제 발동하는가

제품·사이드 프로젝트·PMF/검증 계획에 대한 피드백을 명시적으로 요청할 때. 누구에게 어떻게 검증할지, 살릴지 버릴지, 사전등록·설문·랜딩 기반 검증을 어떻게 볼지 물을 때.

일반 제품 전략 잡담이나 기능 요청에는 발동하지 않습니다.

---

## 핵심 원칙 (불변)

진화는 이 세 가지 위에서만 일어납니다. 원칙 자체는 바뀌지 않습니다.

1. **본질부터 짚는다.** "왜 검증하려는가" 부터.
2. **관심과 행동은 다르다.** 사전등록·설문은 약한 신호. 카드번호·재방문·결제가 진짜 신호.
3. **버릴 것 먼저.** 1등 뽑기보다 버릴 것 정하기가 빠르다.

---

## 7단계 루프

```
① READ      과거 저널 읽기
② SHARPEN   되물어 본인이 진짜 질문에 도달하게 (강한 게이트)
③ DIAGNOSE  본질 짚기 (공통 뿌리 탐색 포함)
④ FEEDBACK  본질 → 분기 → 행동(소요시간) → 납득 사례 → 판단 렌즈
⑤ REFLECT   자기 비판
⑥ JOURNAL   학습 기록
⑦ EVOLVE    스킬 자체 수정 (필요시)
```

② SHARPEN이 1차 게이트입니다. 본인이 표면 질문을 진짜 질문으로 자기 입으로 재정의하기 전에는 진단으로 넘어가지 않습니다. "그냥 답 줘" 압박에도 답을 먼저 주지 않습니다.

⑦ EVOLVE가 자기 진화의 핵심입니다. 같은 종류의 "놓친 것"이 누적되거나 새로운 케이스 유형이 등장하면, 스킬이 진단 질문을 실제로 추가합니다.

---

## 범위와 한계 (정직하게)

이 스킬은 **초기 컨슈머·SMB 제품의 지불의향 검증**에 가장 강합니다. 원칙 2의 신호 위계(카드번호·결제가 진짜 신호)는 그 맥락에서 강한 prior입니다. 보편 법칙이 아닙니다.

맥락이 다르면 1차 신호도 다릅니다. 규제·임상 제품은 인허가와 임상 타당성이, 양면 마켓플레이스는 더 희소한 쪽의 유동성이, 딥테크는 기술 실현성이 지불의향보다 먼저입니다. 이런 경우 ③ DIAGNOSE가 갈라지고, 막히면 ⑦ EVOLVE가 그 맥락 전용 진단 질문을 새로 만듭니다(예: 진단 질문 9, 양면 시장).

요약하면, 단호하게 의견을 내는 스킬입니다. 그 단호함이 가치이자 한계입니다. 출력이 반복적으로 보이면, 그 맥락이 정말 같은 답인지 아니면 진단 질문이 빠졌는지 보십시오. 후자면 그게 EVOLVE 신호입니다.

## 설치

### Claude Code

```bash
git clone https://github.com/bibi-is-typing/kill-or-ship.git
cp -r kill-or-ship/kill-or-ship ~/.claude/skills/
```

별도 setup은 없습니다. journal/ 에 시드 데이터만 들어 있고, 첫 세션부터 7단계 루프가 작동합니다. 실제 케이스는 사용자의 로컬 저널에 쌓이며, 이 저장소에는 올라가지 않습니다.

---

## 시드 케이스 예시

`examples/seed-case.md` 에 가상 케이스가 있습니다.

> **상황**: 3인 팀이 B2B 회의록 자동화 SaaS를 출시 직전. 베타 200명, 광고 채널 고민.
>
> **표면 질문**: "페이스북, 구글, 링크드인 중 어디에 광고 돌릴까요?"
>
> **본질 진단**: 베타 200명은 관심 신호. 광고 결정 전에 카드번호까지 받는 검증이 먼저.
>
> **제시한 행동**: 카드번호 받는 랜딩과 유료 경쟁사 사용자 인터뷰.

이건 초기 컨슈머/SMB 맥락이라 카드번호가 1차 신호인 경우입니다. 규제·양면 시장 케이스에서는 진단이 다르게 갈립니다.
